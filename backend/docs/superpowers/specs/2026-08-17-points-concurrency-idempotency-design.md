# 积分并发安全与业务幂等设计

## 目标

修复积分业务中的并发丢更新、超额消费和重复奖励问题：

- 余额变更必须由数据库条件更新完成，不能依赖 Go 内存中的旧余额。
- 同一个业务事件重复投递时按幂等成功处理，不重复改变余额或写入流水。
- 签到、奖励、文章解锁和特权兑换在同一事务中完成业务记录、余额变更和积分流水写入。
- 并发测试验证最终余额与积分流水变化总和一致。

## 范围

本次修改覆盖 `internal/points` 的仓库层、服务层、实体和迁移测试。

业务事件及幂等键约定如下：

| 业务 | 幂等键 |
| --- | --- |
| 每日签到 | `check_in:{userID}:{date}` |
| 发布文章奖励 | `publish_resource:{userID}:{articleID}` |
| 高质量互动奖励 | `quality_interaction:{userID}:{commentID}` |
| 付费文章解锁 | `unlock_paid_resource:{userID}:{articleID}` |
| 特权兑换 | `redeem_privilege:{userID}:{privilegeKey}` |

幂等键由服务或仓库根据业务参数确定，调用方不直接传入任意字符串。

## 数据模型

新增 `point_operations` 表，负责业务操作的幂等记录和结果保存：

- `user_id`：用户 ID。
- `operation_key`：业务幂等键。
- `change`：本次积分变化，收入为正、支出为负。
- `balance_after`：事务完成后的余额。
- `(user_id, operation_key)` 唯一约束。

`point_ledgers` 增加可为空的 `operation_key` 字段并建立唯一索引。历史流水允许为空，新增流水必须写入业务幂等键；这样既保留已有数据的迁移兼容性，又保证新操作最多对应一条流水。

`point_operations` 和新的流水记录在同一事务中创建。操作记录保存的 `change` 与 `balance_after` 用于重复请求直接返回原业务结果。

## 事务流程

### 收入操作

适用于每日签到、发布文章奖励和高质量互动奖励。

1. 开启事务。
2. 使用 `INSERT ... ON CONFLICT DO NOTHING` 创建 `point_operations`。
3. 如果 `RowsAffected == 0`，说明业务键已经处理，回滚当前事务并查询已有操作结果，直接按成功返回。
4. 对用户执行：
   `UPDATE users SET points = points + ? WHERE id = ?`
5. 校验 `RowsAffected == 1`，否则返回用户不存在。
6. 在同一事务内读取更新后的余额。
7. 创建 `point_ledgers`，写入幂等键、变化量和更新后余额。
8. 更新 `point_operations.balance_after`，提交事务。

### 支出操作

适用于文章解锁和特权兑换。

1. 开启事务。
2. 创建幂等操作记录；重复键走已有操作结果路径。
3. 创建文章解锁或特权兑换业务记录。现有业务唯一约束继续作为第二层保护。
4. 执行条件扣减：
   `UPDATE users SET points = points - ? WHERE id = ? AND points >= ?`
5. 校验 `RowsAffected == 1`。为 0 时查询用户是否存在：用户不存在返回用户错误，用户存在返回 `ErrInsufficientPoints`；事务回滚，不留下业务记录、操作记录或流水。
6. 读取扣减后的余额。
7. 创建积分流水并写入幂等键。
8. 更新操作结果并提交事务。

所有积分变更都保持“业务记录、用户余额、操作记录、积分流水”原子提交，任一环节失败均回滚。

## 并发与重复请求语义

- 同一用户的不同积分操作依赖数据库对用户行的更新锁，不在 Go 中计算旧余额。
- 同一业务键只有一个事务能成功创建操作记录；后续请求读取已提交的操作结果，不重复扣加积分。
- 同一文章解锁和同一特权兑换继续依赖业务表唯一约束，避免历史数据或异常调用绕过幂等键。
- 缓存删除只在事务结束后执行，不改变事务结果。
- 重复请求返回首次成功操作保存的 `balance_after`，不返回“已处理”错误。

## 错误处理

- 条件扣减失败必须区分用户不存在和余额不足。
- 幂等重复必须返回原操作结果。
- 文章或特权的既有业务校验保持不变。
- 唯一约束冲突不应留下部分扣款或部分流水。
- 不把未提交事务中的余额作为返回值。

## 测试设计

新增积分仓库或服务集成测试，使用共享内存 SQLite 数据库并执行完整迁移：

- 100 个 goroutine 并发签到同一用户同一天：只产生一次签到奖励和一条流水。
- 100 个 goroutine 并发发布奖励：每个唯一文章事件只奖励一次。
- 100 个 goroutine 并发高质量互动奖励：每个唯一评论事件只奖励一次。
- 100 个 goroutine 并发解锁同一文章：只成功一次，余额只扣一次，其余请求返回同一幂等结果。
- 并发兑换同一特权：只成功一次，余额只扣一次。
- 并发消费总额超过余额：成功扣减总额不超过初始余额，不出现负数或超额扣减。
- 最终断言：
  `user.points == initialPoints + SUM(point_ledgers.change)`
  且每个业务幂等键最多一条新流水。

测试同时检查失败事务不会残留 `point_operations`、业务记录或流水。
